## 1. 제품 개요

### 한 줄 정의
개인이 자신의 할 일을 등록·정리·완료하는 웹 서비스.

### 해결하려는 문제
기존 할 일 앱은 협업·태그·반복 일정·프로젝트 관리가 얽혀 있어, **"오늘 내가 할 일을 적고 지운다"** 는 단순한 목적에는 과하다. 이 제품은 그 하나만 정확하게 한다.

### 제품 원칙
1. **완료가 주인공이다.** 화면에서 가장 만족스러운 순간은 체크박스를 누를 때다. 시각적·인터랙션 투자는 그곳에 집중한다.
2. **기다리게 하지 않는다.** 완료 토글과 삭제는 서버 응답을 기다리지 않고 즉시 반영한다.
3. **내 것만 보인다.** 다른 사용자의 데이터는 어떤 경로로도 노출되지 않는다.
4. **지운 것은 복구 가능하다.** 물리 삭제를 하지 않는다.

### 성공 기준 (MVP)
`docs/CHECKLIST.md`의 전 항목 통과. 별도의 지표 목표는 MVP 범위 밖이다.

단, **`docs/CHECKLIST.md`는 아직 작성되지 않았다.** 판정 근거가 없으므로 Phase 0에서 이 문서를 먼저 작성하는 것이 MVP의 실질적 선행 조건이다. 체크리스트는 이 문서의 F-xx / NF-xx를 **검증 가능한 행동**(예: "F-21: 삭제 후 DB에서 행이 남아 있고 `deleted_at`이 채워졌는지 확인")으로 옮긴 것이어야 한다.

## 2. 사용자

### 대상 사용자
개인 사용자 1인. 팀·조직·공유 개념은 없다.

### 사용자 유형
| 유형 | 설명 | 특이사항 |
|---|---|---|
| 로컬 계정 사용자 | 이메일 + 비밀번호로 가입 | `provider = LOCAL` |
| 구글 계정 사용자 | 구글 OAuth2로 가입/로그인 | `provider = GOOGLE`, 비밀번호 없음 |
| 비로그인 방문자 | 로그인/회원가입 화면만 접근 가능 | 할 일 데이터에 일절 접근 불가 |

### 핵심 사용자 스토리
- 나는 이메일로 빠르게 가입해서 바로 할 일을 적고 싶다.
- 나는 매번 비밀번호를 치기 싫어서 구글 계정으로 로그인하고 싶다.
- 나는 할 일을 적을 때 목록이나 강조 같은 최소한의 서식을 쓰고 싶다.
- 나는 할 일을 끝냈을 때 바로 체크하고, 끊기는 느낌 없이 화면이 반응하길 원한다.
- 나는 할 일이 쌓여도 진행 중인 것만 골라 보거나 검색해서 찾고 싶다.
- 나는 실수로 지운 할 일이 영영 사라지지 않았으면 좋겠다.

## 3. 범위

### 포함 (MVP)
- 이메일 회원가입 / 로그인 / **서버 로그아웃**
- **Refresh Token 기반 세션 유지 및 자동 토큰 갱신**
- **비밀번호 재설정 (메일 링크 방식)**
- 구글 OAuth2 소셜 로그인
- 할 일 생성 / 조회 / 수정 / 완료 토글 / 삭제
- 목록 페이지네이션, 상태 필터, 제목 검색, 정렬
- 리치 텍스트 본문 (Tiptap)
- Soft Delete
- 라이트/다크 테마
- 반응형 (모바일 ~ 데스크톱)
- Swagger API 문서
- 백엔드 통합 테스트

### 제외 (이번 범위 아님)
| 항목 | 사유 |
|---|---|
| Access Token 블랙리스트 | Refresh Token 폐기로 재발급은 막힌다. 잔여 30분은 허용 범위로 본다 |
| 가입 시 이메일 인증 | 후속. 비밀번호 재설정 메일만 발송한다 |
| 세션 목록 / 다른 기기 로그아웃 화면 | 후속. 비밀번호 재설정 시 전체 폐기로 대체 |
| 회원 탈퇴, 프로필 수정 | 후속 |
| 휴지통 UI, 삭제 복구 화면 | 데이터는 보존되나 화면은 만들지 않음 |
| 태그, 카테고리, 하위 할 일, 반복 일정 | 제품 원칙 위반 (단순함 유지) |
| 파일 첨부 / 이미지 업로드 | 이에 따라 **Amazon S3도 스택에서 제외** |
| 알림, 리마인더 | 후속. **비밀번호 재설정 메일(F-41)은 포함**이며, 그 외 용도의 메일 발송만 제외한다 |
| 공유, 협업, 다중 사용자 | 대상 사용자가 개인 1인 |
| 관리자 화면 | 후속 |
| E2E 테스트 자동화 | 수동 체크리스트로 대체 |
| Docker / 컨테이너 | 요구사항에서 명시적으로 배제 |
| 실제 AWS 배포 수행 | 설정 분리까지만. 배포는 후속 작업 |

## 4. 기능 요구사항

### 4.1 인증

ID는 작성 순서대로 부여되어 있어 번호가 주제별로 연속하지 않는다. **ID 번호는 `docs/ROADMAP.md`가 범위로 참조하므로 변경하지 않는다.** 아래는 주제별로 묶어 읽기 쉽게 정리한 것이다.

#### 가입 · 로그인 (F-01 ~ F-03, F-05 ~ F-07)

| ID | 요구사항 | 상세 |
|---|---|---|
| **F-01** | 이메일 회원가입 | ID는 **이메일만** 사용. 비밀번호 **6자 이상**. 이름 필수. 가입 즉시 로그인 상태가 된다 |
| **F-02** | 중복 가입 차단 | 이미 사용 중인 이메일이면 거부. 단, Soft Delete된 계정의 이메일은 재사용 가능 |
| **F-03** | 이메일 로그인 | 이메일 + 비밀번호. 실패 시 이메일/비밀번호 중 무엇이 틀렸는지 구분해서 알려주지 않는다 |
| **F-05** | 구글 소셜 로그인 | Spring Security OAuth2 **백엔드 주도 리다이렉트** 방식 |
| **F-06** | 계정 연결 | 구글 이메일이 기존 계정과 같으면 **새 계정을 만들지 않고 기존 계정에 연결**한다 |
| **F-07** | 소셜 전용 계정 보호 | 비밀번호가 없는 구글 계정으로 폼 로그인을 시도하면 "구글 로그인을 사용하세요"로 안내 |

#### 토큰 · 세션 (F-04, F-08 ~ F-10, F-38 ~ F-40)

| ID | 요구사항 | 상세 |
|---|---|---|
| **F-04** | 토큰 발급 | **Access Token(JWT, 30분) + Refresh Token(불투명 문자열, 14일)**. Access는 localStorage, Refresh는 **httpOnly 쿠키** |
| **F-08** | 로그아웃 | **서버에 로그아웃을 요청해 Refresh Token을 DB에서 폐기**하고 쿠키를 삭제한다. 클라이언트 토큰 삭제 + 캐시 초기화도 함께 수행한다 |
| **F-09** | 라우트 보호 | 미인증 상태로 보호 화면 접근 시 로그인 화면으로 이동 |
| **F-10** | 만료 처리 | 401을 받으면 refresh를 1회 시도하고, 실패 시 토큰을 지우고 로그인 화면으로 보낸다 |
| **F-38** | 토큰 자동 갱신 | Access Token 만료 시 사용자가 눈치채지 못하게 자동 재발급하고 **원래 요청을 재시도**한다. 동시에 여러 요청이 401을 받아도 **refresh는 한 번만** 실행한다 |
| **F-39** | Refresh Token 회전 | 사용할 때마다 새로 발급하고 이전 것을 폐기한다. **이미 폐기된 토큰이 재사용되면 해당 사용자의 모든 세션을 폐기**하고 재로그인시킨다 |
| **F-40** | 재로그인 시 재발급 | 로그아웃 후 다시 로그인하면 새 Access/Refresh Token이 정상 발급되어 서비스가 이어진다 |

#### 비밀번호 재설정 (F-41 ~ F-45)

| ID | 요구사항 | 상세 |
|---|---|---|
| **F-41** | 비밀번호 재설정 요청 | 이메일 입력 → 재설정 링크 발송. **계정 존재 여부와 무관하게 동일한 응답**을 준다 |
| **F-42** | 재설정 링크 처리 | 링크 진입 시 토큰 유효성을 먼저 확인하고, 유효하면 새 비밀번호(6자 이상) 입력을 받는다 |
| **F-43** | 재설정 토큰 정책 | **1회용, 30분 만료**. 새로 발급하면 기존 미사용 토큰을 무효화한다 |
| **F-44** | 재설정 후 전체 로그아웃 | 비밀번호가 바뀌면 **해당 사용자의 모든 Refresh Token을 폐기**한다. 자동 로그인시키지 않고 로그인 화면으로 보낸다 |
| **F-45** | 소셜 전용 계정 재설정 차단 | 비밀번호가 없는 구글 계정은 재설정 메일을 보내지 않는다(응답은 동일). 로그인 화면에서 구글 로그인을 안내한다 |

## 5. 비기능 요구사항

### 5.1 보안

| ID | 요구사항 |
|---|---|
| **NF-01** | 비밀번호는 BCrypt로만 저장한다. 평문·자체 해시 금지 |
| **NF-02** | **소유권 검증**: 할 일 조회·수정·삭제 시 `user_id` 일치를 **쿼리 단계에서** 강제한다. 조회 후 자바 코드로 비교하지 않는다 |
| **NF-03** | 소유권 위반은 403이 아니라 **404**로 응답한다 (리소스 존재 여부 비노출) |
| **NF-04** | 모든 입력값을 서버에서 검증한다. 클라이언트 검증은 편의일 뿐 신뢰 대상이 아니다 |
| **NF-05** | JWT 시크릿, DB 비밀번호, 구글 클라이언트 시크릿은 전부 환경변수. 저장소에 커밋 금지 |
| **NF-06** | 에러 응답에 스택트레이스·SQL·내부 경로를 노출하지 않는다 |
| **NF-07** | OAuth 리다이렉트 대상은 허용 목록으로 검증한다 (오픈 리다이렉트 방지) |
| **NF-08** | 페이지 크기(`size`)와 정렬 필드는 서버에서 허용 범위·화이트리스트로 제한한다 |
| **NF-09** | Access Token을 localStorage에 두므로 **XSS가 곧 토큰 탈취**다. F-26의 이중 정화가 보안 요구사항이기도 하다 |
| **NF-26** | **Refresh Token은 httpOnly + Secure + SameSite 쿠키로만 전달한다.** 응답 본문이나 localStorage에 절대 넣지 않는다 |
| **NF-27** | Refresh Token과 재설정 토큰은 DB에 **SHA-256 해시로만** 저장한다. 평문 저장·로그 출력 금지 |
| **NF-28** | Refresh Token 쿠키는 `Path=/api/auth`로 제한해 일반 API 요청에 실려 가지 않게 한다 |
| **NF-29** | CORS는 `allowCredentials(true)` + **명시적 origin**. 와일드카드 `*`를 쓰지 않는다. SameSite 값은 로컬(`Lax`)/운영(`None; Secure`)으로 프로파일 분리한다 |
| **NF-30** | 비밀번호 재설정 요청에 **rate limit**(동일 이메일/IP 10분 3회)을 적용한다 |
| **NF-31** | 비밀번호 재설정과 로그인 실패 응답에서 **계정 존재 여부를 노출하지 않는다** |

### 5.2 데이터

| ID | 요구사항 |
|---|---|
| **NF-10** | 모든 삭제는 Soft Delete. `deleted_at`으로 표현한다 |
| **NF-11** | 시간은 UTC로 저장하고 ISO-8601로 주고받는다. 표시 시점에만 로컬 타임존으로 변환한다 |
| **NF-12** | 이메일은 소문자로 정규화해 저장·조회한다 |
| **NF-13** | 살아있는 사용자 기준으로만 이메일 유일성을 보장한다 (부분 유니크 인덱스) |

### 5.3 코드 품질

| ID | 요구사항 |

| **NF-14** | **엔티티를 API 응답으로 직접 반환하지 않는다.** 항상 DTO로 변환한다 |

## 7. 핵심 사용자 흐름

### 7.1 신규 가입 → 첫 할 일
```
/signup → 이메일·비밀번호(6자↑)·이름 입력
       → 검증 실패 시 해당 필드 아래 에러 표시 (F-01)
       → 성공 시 JWT 발급 + localStorage 저장 (F-04)
       → /todos 이동, 빈 상태 "아직 할 일이 없습니다" (F-31)
       → "할 일 추가" → 다이얼로그 → 저장 → 목록 최상단에 표시
```

### 7.2 구글 로그인
```
/login → "Google로 계속하기" (브라우저 이동, fetch 아님)
       → /oauth2/authorization/google → 구글 동의
       → 백엔드: 이메일로 기존 계정 조회
            ├ 있으면 → provider_id 연결 (F-06)
            └ 없으면 → GOOGLE 계정 생성 (password NULL)
       → JWT 발급 → /auth/callback?token=... 리다이렉트
       → 토큰 저장 → /todos
   실패 시 → /login?error=oauth_failed
```

### 7.3 토큰 자동 갱신 (F-38, F-39)
```
API 요청 → 401 TOKEN_EXPIRED
        → POST /api/auth/refresh (쿠키 자동 전송, 본문 없음)
             ├ 성공 → 새 Access Token 저장 + 새 Refresh 쿠키 수신(회전)
             │        → 원래 요청 재시도 → 사용자는 아무것도 눈치채지 못함
             └ 실패 → 토큰 삭제 + 캐시 초기화 → /login
   ※ 동시에 여러 요청이 401을 받아도 refresh는 한 번만 실행하고
     나머지는 그 결과를 기다렸다가 재시도한다 (요청 큐잉)
   ※ refresh 요청 자체는 재시도 대상에서 제외한다 (무한 루프 방지)
```

### 7.4 로그아웃 → 재로그인 (F-08, F-40)
```
로그아웃 클릭
  → POST /api/auth/logout → refresh_tokens.revoked_at 기록 + 쿠키 만료
  → localStorage 토큰 삭제 + React Query 캐시 초기화 → /login
  ※ 이후 refresh를 시도해도 401. 남은 Access Token은 최대 30분간 유효 (알려진 한계 1)

재로그인
  → POST /api/auth/login → 새 Access Token + 새 Refresh 쿠키 발급
  → /todos 정상 진입
```

### 7.5 비밀번호 재설정 (F-41 ~ F-45)
```
/login → "비밀번호를 잊으셨나요?" → /forgot-password
      → 이메일 입력 → POST /api/auth/password/forgot
      → 계정 유무와 무관하게 "재설정 링크를 보냈습니다" 표시
           ├ 로컬 계정      → 메일 발송 (로컬 개발은 콘솔에 링크 출력)
           ├ 소셜 전용 계정 → 발송 안 함 (응답은 동일)
           └ 없는 계정      → 발송 안 함 (응답은 동일)
메일 링크 → /reset-password?token=...
      → GET .../verify 로 토큰 확인
           ├ 유효   → 새 비밀번호(6자↑) 입력 → POST .../reset
           │          → 비밀번호 갱신 + 토큰 사용 처리 + 전체 Refresh Token 폐기
           │          → "비밀번호를 변경했습니다" → /login (자동 로그인 안 함)
           └ 무효/만료 → "링크가 만료되었습니다" + "다시 요청" 버튼
```

### 7.6 완료 토글 (낙관적 업데이트)
```
체크박스 클릭
  → 진행 중 요청 취소, 현재 캐시 스냅샷 저장
  → 캐시 즉시 수정 → 화면 반영 + 완료 연출 재생 (F-27, F-28)
  → 서버 PATCH 요청
       ├ 성공 → 목록·요약 카운트 무효화 후 재조회
       └ 실패 → 스냅샷으로 롤백 + 에러 토스트
```

### 7.7 삭제
```
삭제 클릭 → 확인 다이얼로그 (F-22)
        → 확인 시 목록에서 즉시 제거 (F-27)
        → DELETE 요청 → deleted_at 기록 (F-21)
             ├ 성공 → "삭제했습니다" 토스트
             └ 실패 → 목록 복원 + 에러 토스트
```

## 9. 알려진 한계 (README에 명시할 것)

1. **Access Token은 서버에서 즉시 무효화할 수 없다.** 로그아웃 시 Refresh Token은 DB에서 폐기되어 재발급이 차단되지만, 이미 발급된 Access Token은 남은 유효시간(**최대 30분**)까지 동작한다. 즉시 차단이 필요하면 토큰 블랙리스트나 짧은 만료가 추가로 필요하다.
2. **Access Token을 localStorage에 두므로 XSS가 곧 토큰 탈취**다. 이중 정화(F-26)가 사실상 인증 방어선이다. Refresh Token은 httpOnly 쿠키라 JS로 탈취되지 않는다.
3. **Refresh Token 재사용 감지는 사후 대응**이다. 탈취자가 먼저 사용하면 정상 사용자가 강제 로그아웃되는 방식으로 드러난다.
4. 삭제 데이터는 보존되지만 복구할 UI가 없다 (DB 직접 조작 필요).
5. **메일 발송은 로컬에서 실제로 되지 않는다.** 로컬 프로파일은 재설정 링크를 콘솔에 출력하는 방식이며, 실제 발송은 운영 SMTP/SES 설정 후에만 동작한다.
6. 세션 목록 조회나 "다른 기기 로그아웃" 화면은 없다. 비밀번호 재설정 시에만 전체 세션이 폐기된다.
7. 회원 탈퇴와 프로필 수정 기능이 없다.

### 착수 전 해소해야 할 미충족 선행 조건

아래는 제품의 한계가 아니라 **현재 코드베이스가 이 문서의 요구사항을 아직 충족하지 못하는 지점**이다. 해당 Phase 진입 전에 해소해야 한다.

| 항목 | 막히는 요구사항 | 해소 시점 |
|---|---|---|
| `todo-backend/pom.xml`에 **Jsoup 의존성 없음** | F-26 서버측 sanitize (CLAUDE.md 절대 규칙 8) | Phase 4 진입 전 |
| `todo-backend/pom.xml`에 **SpringDoc 의존성 없음** | F-35, F-36, F-37 (Swagger UI) | Phase 4 진입 전 |
| 백엔드 패키지가 `com.example` | CLAUDE.md 절대 규칙 1 (`com.example.todoapp`) | Phase 1 진입 전 |
| `docs/CHECKLIST.md` 부재 | 전 Phase의 완료 판정 (0장 참조) | Phase 0 |

라이브러리 추가는 CLAUDE.md 규칙 11에 따라 별도 승인이 필요하다.

## 10. 용어

| 용어 | 정의 |
|---|---|
| 할 일 (Todo) | 사용자가 등록한 단일 작업 항목 |
| Soft Delete | 행을 남긴 채 `deleted_at`을 채워 논리적으로 삭제하는 방식 |
| 낙관적 업데이트 | 서버 응답 전에 성공을 가정하고 UI를 먼저 갱신하는 방식 |
| 소유권 검증 | 요청자가 해당 리소스의 `user_id`와 일치하는지 확인하는 절차 |
| 이중 정화 | 서버(Jsoup)와 클라이언트(DOMPurify) 양쪽에서 HTML을 정화하는 것 |
| 계정 연결 | 동일 이메일의 로컬 계정과 구글 계정을 하나의 사용자로 묶는 것 |
| Access Token | 30분짜리 JWT. 매 API 요청의 인증에 사용 |

| 재사용 감지 | 이미 폐기된 Refresh Token이 다시 쓰이면 탈취로 간주해 전체 세션을 폐기하는 것 |
| 계정 열거 방지 | 응답 차이로 특정 이메일의 가입 여부를 알아내지 못하게 하는 것 |
